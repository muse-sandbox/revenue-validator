# ПРОХОД 2: Критерии и рекомендация

**1. Рекомендация:** **revise**, уверенность **high** — потому что все блокирующие пробелы зафиксированы в самом документе как незаполненные шаблоны (не спорная интерпретация), и все они исправимы до запуска; понижения за `insufficient data` к самой рекомендации не применяю, поскольку именно эти пробелы её и обосновывают.

**2. Краткое обоснование.** Документ описывает механику и дизайн армов, но денежная сторона пуста: нет прогноза в $ (S6), нет ни одного центрального коэффициента (S7), нет reach (S5) и power-расчёта (S10) — эффект «+XX%» остался плейсхолдером. Единственные поведенческие данные (S4) сняты на экспайр-подписчиках iOS, тогда как аудитория эксперимента — новые пользователи обеих платформ без прошлой подписки, то есть evidence не переносим на ЦА без поправки. Оффер по документу не меняется (S2), что снимает вопрос эластичности, но строка потерь (S8), план после rollout (S12) и stop-rule (S13) отсутствуют. Это профиль «дозаполнить и запускать», а не «отклонить»: missing data — не основание для deprioritize.

**3. Ожидаемая incremental revenue.** Прогноз автора: отсутствует (S6 — «+XX%» плейсхолдер, $-прогноза нет). Реалистичный диапазон валидатора: **не восстановим**, потому что в документе нет ни reach ЦА (S5), ни baseline CR/ARPU целевого сегмента (S4), ни одного коэффициента модели (S7); данные §1 относятся к другому сегменту и не могут быть подставлены без внешних поправок.

**5. Критичные допущения** (на них держится весь положительный кейс):
- «Gamified scratch конвертирует лучше статичного» — assumption; опирается на generically описанный видео-прецедент (Pre-launch research §2), не на замер этой механики (S2, S14д).
- «Новые free-пользователи конвертируются с первого входа в объёме, достаточном для чтения эффекта» — assumption без baseline (S4, S5 missing).
- «Revealed discount не меняет экономику оффера» — assumption (S2 оговорка, S14в).

**6. Риски каннибализации / refunds / guardrails.** Каннибализация: перехват из других платных входов объявлен как guardrail без числа (S8); сам слот — замена по построению (контроль тоже показывает интерстишел), что ограничивает потери на слоте. Refunds: не упомянуты вовсе (missing). Guardrails (S9) объявлены без порогов; отдельный риск — непропускаемый арм C для day-0 пользователей (S14е): просадка retention этой когорты ударит по всем downstream-потокам.

**7. Stop-rule.** В документе отсутствует (S13). **Предложение валидатора:** остановка арма C при статистически значимой просадке day-1 retention новых пользователей ниже заранее заданного порога; остановка эксперимента при поломке новых scratch/purchase-событий (по инструментальному чек-листу из Experiment design).

**8. Что изменит рекомендацию.**
- → **launch:** SQL-замер reach за 2–4 недели (новые пользователи с первым входом в таб/день, по платформам); baseline воронки текущего статичного интерстишела на этом сегменте (S4); power calc по денежной метрике или объявленному сегменту S11 (S10); строка потерь числом (S8); пороги guardrail + stop-rule (S13); план после rollout (S12).
- → **deprioritize:** если замеренный reach × baseline CR покажет, что даже верхняя реалистичная оценка эффекта ≤ 0 или ниже бизнес-порога; сам бизнес-порог в документе не задан — это надо зафиксировать явно.

**9. Список `missing`:** доля трафика (S3); baseline ЦА (S4); reach/день (S5); денежная модель и $-прогноз с горизонтом (S6); центральные коэффициенты (S7); строка потерь числом (S8); MDE/power/alpha/sample/duration (S10); план измерения после rollout (S12); stop-rule (S13); величина «revealed discount» по армам (S2/S14в); упоминание refunds.

# ПРОХОД 3: Продуктовый review механики

**1. Оценка механики + главный риск.** Механика (S2/S3): игровой scratch-to-reveal купон на первом входе в таб, 1 показ на пользователя, только day-0 free-пользователи, оффер тот же — меняется подача; арм C непропускаемый. Поведенческая ставка: интерактивное «стирание» создаёт любопытство и ощущение «выигранной» персональной скидки, поднимая вход в paywall против статичного экрана. В контексте продукта ставка частично правдоподобна: в корпусе формат/креатив на этой поверхности действительно двигал результат материально (KS-04), а скидочный (не-trial) оффер — правильный тип для free-сегмента (IKB-P09). Против неё работают два обстоятельства: механика добавляет шаг взаимодействия ДО оффера, и целится в самый холодный из возможных подсегментов — пользователей нулевого дня, ещё не получивших ценности продукта, при том что самый отзывчивый сегмент (ex) исключён по построению (IKB-P06). **Главный продуктовый риск:** отклик day-0 free-базы может быть слишком мал, чтобы механику вообще было видно, а scratch-шаг может фильтровать вход в paywall, а не вовлекать (confidence вывода: medium; evidence: S3, S4-missing, IKB-P05, IKB-P06).

**3. Product-specific recommendation.**
1. До запуска замерить reach и baseline воронку day-0 сегмента (см. п.4) — без этого итерация повторяет риск KS-01 (IKB-P01).
2. Технически проверить определение «новый пользователь без прошлой подписки» при переустановке приложения; из-за незакрытого unified_id bug (KS-05/KS-06 §Execution) добавить обязательный разрез чтения по прошлым правам (IKB-P10).
3. Добавить в analysis plan сегмент чистоты «without interstitial accesses» / подписки из других источников — заявленных сегментов S11 недостаточно для чтения каннибализации (IKB-P02: этот разрез стал обязательным в KS-03…KS-06).
4. Инструментировать scratch-воронку пошагово (show → scratch start → reveal → paywall open → purchase) и заранее задать критерий сравнения «показ→paywall» варианта B/C против контроля — прямая проверка гипотезы IKB-P05 о фильтрующем шаге; рассмотреть авто-reveal через N секунд как fallback.
5. Для арма C заранее задать порог day-1/7 retention новых пользователей и stop-rule (IKB-P12: guardrail обязателен, знак непредсказуем; для day-0 когорты цена ошибки максимальна).
6. Сохранить «1 показ на пользователя» (IKB-P03), но не экстраполировать CR первого показа на будущие частотные итерации программы.
7. Зафиксировать письменно величину «revealed discount» по армам и её тождество стандартному intro-офферу — иначе это смена оффера (зона К1 прохода 2), а по IKB-P07 рост щедрости притягивает низко-интентных.
8. Замерить fail-rate рендеринга scratch-экрана (вибрация/анимация) на слабых устройствах — фактическая экспозиция, а не число триггеров (IKB-P11).

**4. Самый дешёвый решающий замер.** SQL за 2–4 недели по текущему поведению, две цифры: (а) дневное число новых пользователей (завершивших install tour), доходящих до первого входа в таб, по платформам; (б) воронка ТЕКУЩЕГО статичного интерстишела на этом же сегменте: показ → открытие paywall → покупка. **Подтверждено:** reach × baseline-покупки дают за разумную длительность выборку покупок, достаточную для power calc из прохода 2 (порог задаётся этим расчётом), т.е. day-0 база в принципе откликается на интерстишел. **Опровергнуто:** покупки новых пользователей с первого интерстишела — единицы в неделю; тогда никакой креатив на этом trigger/сегменте нечитаем (сценарий KS-01), и менять надо сегмент/триггер, а не подачу.

**5. Численные vs продуктовые concerns.**
- Численные (проход 2, только ссылки): К2 insufficient data (модель), К3 concern средний (строка потерь), К4 insufficient data (reach/sample), К5 insufficient data (мощность под деньги), К6 concern средний (post-rollout/stop-rule).
- Продуктовые (проход 3): (a) самый холодный сегмент — day-0 free при исключённых ex (IKB-P06/P09); (b) scratch-шаг может фильтровать до оффера (IKB-P05, single-case гипотеза); (c) retention-риск непропускаемого арма C на day-0 (IKB-P12); (d) утечка переустановившихся ex в «новых» (IKB-P10); (e) неподтверждённый reach сегмента (IKB-P01); (f) отсутствие сегмента чистоты (IKB-P02); (g) рендеринг/доставка сложного креатива (IKB-P11).
