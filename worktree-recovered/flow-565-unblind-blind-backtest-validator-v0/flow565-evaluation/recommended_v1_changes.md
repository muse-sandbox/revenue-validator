# FLOW-565 — Рекомендованные изменения V1 (без повторного запуска на holdout)

⚠️ После применения любого из пунктов эти 8 кейсов — development set; для следующего независимого backtest нужен новый holdout. Ни один изменённый промпт на HX-01…HX-08 не запускался.

## 1. Разрушить all-revise saturation (главное)

V0 выдал `revise` на 8/8 — класс действия не несёт сигнала. Варианты (взаимодополняющие):

- Ввести явные условия для `launch`: если нет критичных concerns и дизайн внутренне консистентен → `launch` (возможно с списком non-blocking правок). Сейчас промпт де-факто позволяет `launch` только идеальному документу, которых в корпусе нет.
- Разделить `revise` на два класса: `revise-blocking` (запуск в текущем виде вероятно приведёт к неизмеримому/отрицательному результату: недостижимый sample, немощный дизайн, неизмеримые деньги) и `revise-nonblocking` (запускать можно, параллельно закрыв правки). На этом корпусе это дало бы дискриминацию: HX-02/04/05 — blocking (подтверждено GT), HX-07/08 — nonblocking.
- Требовать отдельным полем **предсказанный класс исхода** (positive / negative / inconclusive-NM с вероятностями или рангом) — прямо улучшает измеримость следующего backtest и полезность для приоритизации.

## 2. Формализовать проверку «дизайн ловит собственный прогноз»

Самый сильный единичный тест V0 — HX-08: сравнение MDE с прогнозным лифтом автора (107.6% vs +46.9% → «тест не может подтвердить собственную модель»). Сделать обязательным шагом для каждого кейса: `MDE ≤ прогнозный эффект?`; `sample × duration достижимы при замеренном reach?`; `метрика решения = метрика мощности?`. В V0 это происходило, но не как гарантированный чек-лист с явным вердиктом по каждому пункту.

## 3. Калибровка severity/уверенности на предсказание исхода

- Уверенность V0 отражает качество документа, не риск слота. Добавить второе поле: «риск запуска как есть» (low/medium/high) — на этом корпусе высокий риск корректно лёг бы на HX-02/04/05 (недостижимый дизайн) против HX-07/08.
- Явно оговаривать в ответе свойство doc-bounded диапазонов: «диапазон ограничен числами документа; если ошибочен сам документ, фактический эффект может выйти за диапазон в любую сторону» (урок HX-06: [−$445;+$133]/нед против факта ~+$1024/день).

## 4. Компактность для human-review

80–97 строк на ответ. Добавить обязательный заголовочный блок ≤10 строк: рекомендация, класс риска, топ-3 concerns с числами, единственный самый дешёвый решающий pre-launch замер. Остальное — как приложение. (Машинное время в норме — 2–3 мин/кейс; экономим время человека.)

## 5. «Самый дешёвый решающий замер» как отдельное поле

V0 в §8 фактически предлагал такие замеры (и в HX-02/03/04 они точно вскрыли бы провал до запуска: SQL-замер reach; конверсия существующего tour update; источник «338 инсталлов»). Вынести в обязательное структурированное поле: `decisive_prelaunch_check: {что замерить, чем (SQL/дашборд), что докажет}` — это главный практический выход валидатора для команды.

## 6. Сохранить без изменений (подтверждено backtest'ом)

- Детекция циркулярного reach (reach ≡ sample ÷ duration) — сработала в HX-01/04.
- Требование двусторонней модели gains−losses и явной строки потерь — подтверждено HX-05/06.
- Дисциплина «missing остаётся missing», запрет инвентированных чисел, показанная арифметика производных — 8/8 чисто.
- Игнорирование post-launch вставок и плейсхолдеров шаблона — сработало (HX-01, HX-08).
- Правило «deprioritize нельзя из-за отсутствия данных / малости эффекта без бизнес-порога» — предотвратило false blockers на HX-07/08.

## 7. Процессные рекомендации к следующему backtest

- Включать исходные HX-карточки в evaluation bundle — чтобы evidence discipline проверялась пословно, а не через GT-повтор чисел.
- Требовать от ground truth раздельные записи на итерацию (HX-06: positive ит.1 + negative ит.2 сжаты в один класс кейса) и фиксировать правило агрегации заранее.
- Для метрики usefulness заранее назначить независимого ревьюера (не evaluator'а) — протокол этого требует, в FLOW-565 роль совмещена.
