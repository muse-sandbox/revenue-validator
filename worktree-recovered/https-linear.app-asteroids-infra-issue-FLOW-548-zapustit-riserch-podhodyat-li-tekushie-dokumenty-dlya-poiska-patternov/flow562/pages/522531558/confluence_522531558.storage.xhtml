Hypothesis

If we display a permanent banner to the audience that canceled auto-renewal but still has access, and in this banner, we mention the imminent loss of benefits, we will generate an additional $X in revenue because a portion of the audience will renew their subscription to avoid losing premium features.

Description of the Solution & Mockups

  • Experiment for users who canceled auto-renew but still have access  
    • only for those who purchased access on the web  
    • if the user has access purchased in the app, they are not included in the experiment
    • we’re preparing an experiment only for PRO in 1 iteration
  • Two weeks before access ends, display a non-dismissible permanent banner with a countdown to the end of access
  • The banner message will inform the user that their subscription is ending and offer to maintain access  
  • After clicking the banner, show a modal window  
    • The modal will display a list of features the user will lose if access is not renewed  
      • Will we be able to display the modal window at the point where it is triggered?
    • Since the user has previously purchased access, we already have their payment details, so we won't ask for them again  
    • Clicking the button on the modal will enable auto-renewal of the current subscription ( confirm)
  • After activation, we display a success window
  • After closing the success window, we return to the original page where the subscription reactivation process began
  • The permanent banner is hidden in this case
  • After renewing the subscription, we change the subscription status to "Active" with a "Details" button for potential further actions
  • FAIL
    • if we fail to create a new subscription to Braintree, we will try several times without the user.
    • if we get an error after all our attempts, we should inform the user, for example by mail. In the mail, you can add an action button to re-create the subscription.

Decision

Results

  • 8% conversion to successful resubscribe 
  • yet hadn't increase recurrent charges
    • only 30% of resubscribers actually charged on billing date
      • most of the others had their transaction decline (status: PROCESSOR_DECLINED)
    • earned even less from them
  • problems
    • bad split routine: 4% of users in experiment had multiple variations
    • very few users. got less than 1k for 1+ month. while expected to get this amount in a few days

Conclusions 

  • can't rollout this test variation

  • first of all find out the problem with small sample size in experiment

  • can ask users to update their card info after resubscribing
