# FLOW-577 — Inventory исторических revenue-экспериментов (V0)

человеком-аналитиком не проводилась** (см. «Ограничения»).

Разметка выполнена по модели релевантности **FLOW-574** (блоки A/B/C, 10 осей)
со словарём этапов из **FLOW-576** (Revenue User Flow V0, S0–S9). Якорь типологии —

DOCS-страница 777830942).

## Как фильтровать и сравнивать (правила из FLOW-574)

1. **Гейт валидности (блок A):** кейсы с `result_class: inconclusive` и кейсы
   с загрязнёнными величинами (T2-06 — баг таргетинга; T1-02 iter1) не являются
   основанием продуктового вывода — только measurement-уроками.
2. **Уровень близости** нового кейса к историческому считается по осям блока B
   (`exact / adjacent / different` — §2–3 модели): L1 требует mechanism + flow_stage
   exact и сопоставимого сегмента; совпадение только по `metric` (тип 3) даёт L3 —
   baseline, дисперсию, guardrails и ловушки измерения, но не продуктовый вывод.
3. **Переносится всегда только знак и механизм**; величины эффектов из
   `plan_fact`/`ci` — только как prior для sizing с явной пометкой.
4. `source_confidence: mirror-annotation` (все кейсы типов 2–3) означает: разметка
   построена по аннотации локального зеркала базы гипотез, и **`result_class` у таких
   кейсов — предварительный** (аннотации часто не содержат p-values; поле `ci`
   говорит, извлечены ли они). Гейт §4.6 модели FLOW-574 читает именно
   `result_class`, поэтому до сверки со страницей Confluence (`A.page`)
   mirror-кейс допустим только как L3-материал (sizing / measurement / guardrails),
   даже если оси дают L1/L2; поля «не проверено» заполняются при сверке.
5. `result_class: mixed` — расширение словаря модели V0 (разные исходы по
   платформам/рукам). Предложение для модели V0.1: hard filter применяется к той
   платформе/руке, чей вывод переносится (см. шапку `inventory.yaml`).

## Пример фильтрации к якорной идее (демо)

Для новой идеи «изменить оффер в App-интерстишле для free-аудитории»:
L1 — T1-02, T1-06, T1-10 (mechanism offer-structure exact, stage/surface exact,
free exact); L2 — T1-05/T1-08 (тот же слой, но сегмент ex-paid — different),
T3-06 (mechanism trial→instant exact, но surface/flow different); L3 — T3-02/T3-03/T3-04
(метрика та же, механизм price/plans на web). Противоречие для репорта: intro-скидка
работает на free (T1-06 iter2), но 3/6-мес intro-планы на web каннибализируют
годовые (T3-03) — конфликт разрешается осью surface/flow_stage.

## Кросс-корпусные наблюдения (интерпретации, не факты)

- **Instant вместо trial** подтверждён в трёх разных flow: интерстишл ex-paid
  (T1-08), интерстишл free iOS (T1-10, surface-чтение), внутренние пейволлы iOS
  (T3-06) — с одинаковой ценой риска (LTV/renewal дискаунт-когорты) и одинаковым
  And-ограничением эластичности (T1-10, T3-01).
- **CTR/attention ≠ intent** повторяется на трёх поверхностях: T1-09 (paywall→click
  ×0.5 при персонализации обёртки), T2-04 (CTR +35–47% без конверсии), T1-07
  (нескипаемость ×8 вовлечение при retention-цене).
- **Лишний шаг воронки = мультипликативный drop-off**: T1-03 (96% на pre-paywall),
  T2-07 (демо-пауза −36% access CR).
- **Состав меню планов хрупок в обе стороны**: добавление (T3-03) и удаление (T3-04)
  планов ломают баланс якорей.

## Ограничения (честные пробелы V0)

1. Для типов 2–3 validity-поля (`srm_ok`, `maturity_ok`, точные CI) из зеркала
   не восстановимы — помечены «не проверено»; тип 1 верифицирован по карточкам
   FLOW-568/571 (KS-*/GT-IH-*, построены по snapshot'ам Confluence).
2. Кейс 761947509 (Explore product widget, 7085/7130/7229) исключён: исход
   не восстанавливается из зеркала (см. `meta.excluded`).
3. Web-кейсы T3-02/T3-03 не имеют AB id в зеркале (web-эксперименты вне
   `ab_experiment`-реестра либо id не зафиксирован в аннотации).
4. Непокрытые классы (найдено агентным ревью; кандидаты на расширение V1):
   - **tour/onboarding paywall (S3)** — главная конверсионная поверхность App —
     не представлена ни одним кейсом; новые идеи этого класса сейчас будут ложно
     искать ближайшие аналоги среди interstitial-кейсов;
   - **lifecycle S7–S8** (trial length, price increase, refund/cancel-flow,
     pause-офферы) представлен единственным кейсом T2-05;
   - ось B6 всюду Pro/Pro+ — нет OTP / songbooks / courses-кейсов; CRM/push/email
     вход (S1) не представлен (пробел уже помечен во FLOW-576 §7).
5. Проверка полноты и корректности разметки человеком-аналитиком — следующий шаг
   (агентное ревью проведено: вердикт APPROVE-WITH-FIXES, правки применены;
   см. итоговый комментарий FLOW-577).
