Описание

В приложении присутствует реклама на табовой, которая показывается по определенным правилам:

  • Максимум 5 показов в день.
  • Следующую рекламу можно показать не менее чем через 180 секунд после показа предыдущей
  • Мы не показываем рекламу на том же табе, на котором была показана последняя просмотренная реклама (если пользовать посмотрел рекламу на Highway to Hell, он может выйти из таба и зайти через более чем 180 секунд, но реклама снова не появится на этом табе)

Local interstitial — это внутренний экран-предложение, который показывается пользователю вместо рекламной паузы в табах.
Его задача: мягко перевести пользователя к покупке подписки без резкого “обрыва” пользовательского опыта.

Техническая реализация

Основные сущности
  • adResolver (@muse-native/advertisement/.../AdResolver.ts)
    • Низкоуровневый резолвер ad-лимитов/состояния показа interstitial.
    • Хранит per-day ad-состояние в marketingHolder.preferences.ads.
  • AdService (src/services/AdService.ts)
    • Оркестратор выбора какой local сценарий запускать вместо/в рамках ad-попытки.
    • Определяет сегмент пользователя и source (AD_FREE_INTERSTITIAL, AD_FREE_WINBACK_INTERSTITIAL, AD_FREE_INTERSTITIAL_WITH_CODE, MONETIZATION_VIDEO).
  • marketingHolder.onFeatureAction({ source })
    • Универсальная точка входа в marketing UI flow; дальше source маршрутизируется в FeatureMarketingComponent -> FloAdFreePaywall.
  • AdFreeBanner (src/.../AdFreeBanner.tsx)
    • Параллельный (ручной) канал входа в тот же paywall-пайплайн через баннерные source (AD_FREE_TAB, AD_FREE_WINBACK_TAB).
Как работает ad-слой

AdResolver декларирует ограничения:

  • timeInterval = 180000 (3 минуты),
  • updateCount = 5 (до 5 показов/день),
  • хранение по дате YYYY-MM-DD.

Пайплайн:

  • onWillShow(tabType, adKey) — проверка возможности показа.
  • onShow(adKey) — фиксирует lastAdKey.
  • onDidShow() — уменьшает дневной count, обновляет lastAdDate.
  • onFailedToShow() — сигнал в marketingHolder.onAdFailedToShow().
Как работает оркестрация local сценариев

AdService.tryShowInterstitial(tabType, adKey) вызывает interstitialManager.tryShowAds(...) с двумя ключевыми колбэками:

willShow

Решает, какой local source запускать (приоритетно):

  1. AD_FREE_WINBACK_INTERSTITIAL (если ex-pro и не сконверчен в этом flow ранее),
  2. AD_FREE_INTERSTITIAL (offer-сегмент без истории подписок),
  3. MONETIZATION_VIDEO (Android + online + нет активных прав).

Каждый запуск проходит через tryShowLocalInterstitialOncePerDay(...):

  • ключ: @MonetizationInterstitialTimestamp,
  • ограничение: не чаще 1 раза в день,
  • при успехе: marketingHolder.onFeatureAction({ source }) + registerShow(adKey).

onError

Fallback-ветка, если ad не показалась:

  • повторно выбирается featureKey по сегменту (offer -> winback -> video),
  • если есть featureKey и сплеши не отключены: marketingHolder.onFeatureAction({ source: featureKey }) + registerShow(adKey).
Баннерный канал

getAdFreeBanner() возвращает баннер по сегменту:

  • если стоит @AdFreeInterstitial:isSubscribed -> баннер не показывается;
  • !hadAnyRights() -> баннер с source: AD_FREE_TAB + discount UI;
  • isExProSubscriber() -> баннер с source: AD_FREE_WINBACK_TAB.

Клик по баннеру:

  • marketingHolder.onFeatureAction({ source }),
  • дальше тот же маркетинговый роутинг в paywall flow.
Если добавляем новый local interstitial

  • 1. Новый source-ключ

    • Добавить константу в marketingConsts (по аналогии с AD_FREE_* / MONETIZATION_VIDEO).
    • Сразу продумать analytics-имя в SOURCE_MAP (feature + analytics).

  • 2. Логика выбора сценария (AdService)

    • Встроить новый кейс в tryShowInterstitial:
      • условия сегмента,
      • приоритет относительно существующих веток,
      • попадание в willShow,
      • fallback в onError (если нужно).
    • Решить, должен ли сценарий идти через общий day-cap (tryShowLocalInterstitialOncePerDay) или свой лимит.

  • 3. Роутинг в UI (FeatureMarketingComponent)

    • Добавить source в isLocalInterstitialSource() (или соответствующий роутинг), чтобы source реально открывал нужный paywall/container.
    • Проверить, не ломает ли это существующие исключения/ветки.

  • 4. Контейнер/экран сценария

    • Либо использовать существующий FloAdFreePaywall, либо создать отдельный container.
    • Если есть pre-screen, определить:
      • тип pre-screen,
      • таймер/закрытие,
      • переход в основной paywall,
      • поведение back/dismiss.

  • 5. Продукты и коммерческая конфигурация

    • В data.tsx/резолвере source-типа прописать:
      • какие SKU показываем (primary/secondary/special),
      • как презентуем цены/дисконт/trial,
      • platform-особенности (iOS/Android).
    • Проверить, соответствует ли копирайт реальному офферу.

  • 6. Маркеры состояния

    • Определить, какие visited-маркеры нужны:
      • “уже сконверчен”,
      • “уже видел pre-screen”,
      • одноразовые/дневные ограничения.
    • Явно описать, где маркер ставится и где читается.

  • 7. Баннерный канал (опционально)

    • Если нужен баннерный вход — добавить в AdFreeBanner/getAdFreeBanner (или новый баннерный компонент):
      • условия показа,
      • source при клике,
      • блокировку для already-converted пользователей.

  • 8. Аналитика

    • Минимум: вход в сценарий, view pre-screen, view paywall, CTA click, purchase click/success, dismiss/close.
    • Проверить, что sourceForAnalytics корректно отдает новое значение.
    • Убедиться, что события не дублируются между pre-screen и paywall.

  • 9. Приоритеты и конфликты

    • Новый сценарий почти всегда конфликтует с существующими ветками (offer/winback/video), поэтому важно зафиксировать порядок выбора.
    • В документации явно указать: “какой сценарий выигрывает при пересечении условий”.

  • 10. Практическая проверка перед релизом

    • happy path (willShow),
    • fallback (onError),
    • day-cap,
    • поведение маркеров,
    • Android/iOS расхождения,
    • наличие/отсутствие баннерного входа,
    • корректность аналитических source и событий.
