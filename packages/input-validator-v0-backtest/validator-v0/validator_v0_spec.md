# Validator V0 — спецификация

Версия: **V0 (frozen 2026-08-03)**. Статус: заморожен до blind backtest (см. `validator_v0_freeze.md`).

## 1. Назначение и scope

Validator V0 — pre-launch валидатор денежной стороны продуктовой гипотезы. Он читает **только информацию, существовавшую до результата эксперимента** (pre-launch snapshot документа гипотезы), и выдаёт одну рекомендацию:

- `launch` — запускать;
- `revise` — сначала доработать;
- `deprioritize` — не приоритизировать.

**В scope:** incremental revenue (net gain − loss), ARPU/revenue, каннибализация соседних денежных потоков, refunds, достижимость эксперимента (reach/sample), измеримость денежного результата (мощность, план измерения после rollout).

**Вне scope:** ФОТ, стоимость разработки, затраты проектного процесса, денежная стоимость экспериментального слота, UX/стратегические соображения вне денег. Валидатор не заменяет расчёты агента-аналитика и не принимает финальное решение — оно остаётся за владельцем бизнес-решения.

Ключевой принцип (из AI Revenue Decision Loop): не запущенный проект нельзя помечать `FAIL`; `deprioritize` — это «не инвестируем сейчас», а не приговор идее.

## 2. Input schema — минимальный pre-launch snapshot

Snapshot собирается из документа гипотезы (структура соответствует Document template: Pitch → Context & Idea → Confidence research → Reach & Impact → Hypothesis → Experiment design → Solution → Analytics). Каждое поле имеет **значение**, **тип** и **ссылку на раздел документа-источника**.

### Типы полей

| Тип | Определение |
|---|---|
| `fact` | Наблюдаемое значение с источником: замер, SQL/Redash/Metabase-запрос, таблица текущих метрик, результат прошлого эксперимента/рисерча, зафиксированное описание решения/конфига. |
| `assumption` | Допущение без прямого замера, в т.ч. мнение автора («probably», «из головы»), порог, выбранный без данных. |
| `forecast` | Расчётная величина модели (прогнозный lift, прогноз revenue, sample size из калькулятора) — производная от facts и assumptions. |
| `missing` | Поле в документе отсутствует, пусто или осталось шаблонным плейсхолдером. |

**Правила классификации (STRICT):**
1. Отсутствующее значение **запрещено достраивать догадками** — оно фиксируется как `missing` и попадает в список missing выходного отчёта.
2. Текст шаблона и демонстрационные значения (примеры вида «1533 / 3.65% / $2121», «N%», «[value %]», «Delete this info block…») **не являются данными проекта** — поле с плейсхолдером = `missing`.
3. Значение, выведенное валидатором из других полей (например, reach/день = sample ÷ duration), помечается как **производное** с указанием исходных полей; оно не становится `fact`.
4. Мнение автора без данных («мы верим, что…») — это `assumption`, даже если сформулировано утвердительно.

### Поля snapshot

| # | Поле | Что фиксировать | Ожидаемый раздел документа |
|---|---|---|---|
| S1 | Контекст: цель и «почему сейчас» | Формулировка цели, обоснование срочности | Pitch / Context & Idea |
| S2 | Изменение | Что конкретно меняется для пользователя; меняется ли **цена/оффер** (флаг для К1) | Context & Idea / Solution |
| S3 | Аудитория и сценарий | Сегмент, платформа, точка воронки (exposure), доля трафика | Hypothesis / Experiment design / Analytics |
| S4 | Baseline | Текущие значения target-метрики и денежных метрик для целевой аудитории, источник замера | Reach & Impact / Current metrics |
| S5 | Reach | Users/day в сценарии; чем замерен (SQL за 2–4 недели / выведен / отсутствует) | Reach & Impact |
| S6 | Денежная модель | Явная цепочка поведение→деньги (A/B test model); прогноз incremental revenue в $ и **временной горизонт** | Reach & Impact / A/B test model |
| S7 | Центральные коэффициенты и evidence | Каждый коэффициент цепочки (CTR, CR, доля, ARPPU…) + его evidence (замер / прошлый эксперимент / ссылка) или отметка об отсутствии | A/B test model / Confidence research |
| S8 | Gains, losses и каннибализация | Есть ли в модели строка потерь числом: каннибализация соседних потоков, субституция планов, refunds, потеря downstream-платежей | A/B test model |
| S9 | Target и guardrail metrics | Goal-метрика; объявленные guardrails (дефолтный сет шаблона: ARPU, Retention 7d / active days, users with 3+ tabs weekly; для web free — bounce rate) | Hypothesis / Experiment design |
| S10 | MDE, sample size, duration | Baseline/lift/MDE/power/alpha/sample per variation/duration; **для какой метрики посчитан MDE** (конверсионной или денежной) | Experiment design |
| S11 | Запланированные сегменты чтения результата | Разрезы/конфиг сегментов, объявленные до запуска (в т.ч. сегмент чтения денег) | Experiment design / config |
| S12 | План измерения после rollout | Holdout-доля или observational-протокол (метрика, окно, контроль сезонности), объявленные до запуска | Post-Rollout Analysis / Decision |
| S13 | Stop-rule | Заранее определённые условия остановки эксперимента/раскатки | Experiment design / Decision |
| S14 | Открытые вопросы и противоречия | Внутренние противоречия документа (расходящиеся sample/duration, незаполненные гипотезы и т.п.) | весь документ |

## 3. Критерии

К1–К6 определены в `validator_v0_criteria.md`. Каждый критерий получает ровно один статус: `pass` / `concern` / `insufficient data` (+ `pass (n/a)`, когда критерий по определению неприменим — фиксируется с обоснованием). **Веса и суммарный score не назначаются** — на выборке из 12 неоднородных экспериментов нет доказанных оснований для весов; рекомендация выводится через decision logic ниже, а severity каждого concern оценивается индивидуально по карточке критерия.

## 4. Decision logic

Шаг 1. Применить К1–К6 к snapshot (проход 2 промпта). Для каждого `concern` определить severity (критичный / средний) по правилам карточки.

Шаг 2. Построить **реалистичный сценарий** incremental revenue: взять модель автора и скорректировать её только documented-способами (заменить необоснованные коэффициенты на консервативные из evidence того же документа; добавить строку потерь = 0…оценка сверху из собственных данных документа). Никаких выдуманных чисел: если коррекция невозможна без внешних данных — диапазон помечается как невосстановимый.

Шаг 3. Рекомендация:

- **`launch`** — нет критичных concern; реалистичный сценарий модели показывает положительный incremental impact; эксперимент способен проверить денежный результат (К4/К5 не критичны: sample достижим, деньги читаемы по основной метрике или заранее объявленному сегменту). Средние concern не блокируют `launch`, но обязаны попасть в output как **условия запуска** (например: «до старта зафиксировать observational-протокол» — правка процесса, не модели).
- **`revise`** — есть **исправимый** пробел в модели, evidence, reach, мощности, guardrails или плане измерения, без устранения которого решение о запуске принимать нельзя (любой критичный concern; или `insufficient data` по критерию, определяющему знак/проверяемость денег). Каждый `revise` обязан содержать конкретный способ исправления (из карточки критерия, поле «что снимает concern»).
- **`deprioritize`** — только если **после реалистичной коррекции допущений** (шаг 2) ожидаемый incremental impact ≤ 0, либо идея нарушает заданный бизнесовый порог (когда он появится).

Ограничения (STRICT, пока бизнесовый hurdle rate не задан):
- **не** отклонять идею только потому, что положительный impact кажется маленьким;
- **missing data не является основанием для `deprioritize`** — это `revise` (если пробел исправим) или `insufficient data` по критерию;
- если для portfolio prioritization не хватает бизнесового порога — явно писать это в output («impact положителен, но мал; для приоритизации нужен hurdle rate от владельца бизнес-решения»).

Уверенность рекомендации: `high` / `medium` / `low` — понижается при каждом `insufficient data`, при невосстановимом диапазоне impact и при внутренних противоречиях документа (S14).

## 5. Output schema

Ответ валидатора (проход 2) обязан включать, в этом порядке:

1. **Рекомендация** (`launch` / `revise` / `deprioritize`) + **уверенность** (high/medium/low, с одной фразой почему).
2. **Краткое обоснование** (3–5 предложений, специфичных для проекта, не generic checklist).
3. **Ожидаемая incremental revenue**: прогноз автора и реалистичный диапазон валидатора ($/горизонт), если он восстановим из данных документа; иначе — явное «диапазон не восстановим, потому что…».
4. **Таблица К1–К6**: критерий | статус | severity | одно предложение-обоснование со ссылкой на поле snapshot (S#) и evidence.
5. **Критичные допущения** — список полей типа `assumption`/`forecast`, на которых держится положительный impact.
6. **Риски каннибализации / refunds / guardrails** — какие соседние денежные потоки затронуты и чем это грозит incremental revenue.
7. **Stop-rule** — существующий из документа или предлагаемый (помеченный как предложение валидатора, не как данные документа).
8. **Что изменит рекомендацию** — конкретные данные/правки: для `revise` — что исправить, чтобы стало `launch`; для `launch` — что должно вскрыться, чтобы стало `revise`/`deprioritize`.
9. **Ссылки на поля и evidence** — каждое утверждение опирается на S#-поле snapshot и раздел исходного документа.
10. **Список `missing`** — все отсутствующие поля, без выдуманных значений.

## 6. Процесс применения

Промпт (`validator_v0_prompt.md`) выполняет два раздельных прохода: (1) извлечение и классификация snapshot без какой-либо рекомендации; (2) применение К1–К6 и формирование рекомендации строго по snapshot прохода 1. Смешивать проходы запрещено: проход 2 не имеет права возвращаться к исходному документу за «ещё одним фактом», не занесённым в snapshot.
