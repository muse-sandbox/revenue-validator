# ПРОХОД 2: КРИТЕРИИ И РЕКОМЕНДАЦИЯ

## 1. Рекомендация + уверенность

**`revise`**, уверенность **low** — оба центральных коэффициента модели (30%, 1%; S7) не имеют evidence, строка потерь на поверхности с sales-баннером отсутствует (S8), а реалистичный диапазон impact не восстановим из данных документа.

## 2. Краткое обоснование

Весь прогноз +$330/+$387 за период (S6) держится на двух коэффициентах без единого замера: 30% view rate карточки и 1% конверсии просмотр→Access (S7) — при этом исследования, которые должны были их обосновать, стоят в документе как TBD (S14). Поверхность Explorer несёт как минимум два соседних денежных потока — sales-баннер (документ сам заявляет проверку «синергии») и базовую воронку Access 1d новых инсталлов (S3) — но модель односторонняя: все +28/+32 access приняты инкрементальными, потери не оценены числом (S8), хотя субституция базовой конверсии 3.59%/1.78% может съесть gain целиком. Сильные стороны дизайна: MDE честно посчитан по денежной метрике ARPU (S10), сегменты платформ разделены (S11), цена/оффер не меняются (S2). Пробелы исправимы замерами — оснований для deprioritize нет.

## 3. Ожидаемая incremental revenue

- **Прогноз автора:** +$330 (iOS) + $387 (Android) за модельный период; сам период не подписан (предположительно сутки — S6/S14), годовая экстраполяция — missing.
- **Реалистичный диапазон валидатора: не восстановим**, потому что (а) в документе нет ни одного замера для замены коэффициентов 30% и 1% на консервативные значения (Research — TBD, S7/S14); (б) нет данных для оценки сверху строки потерь (объёмы/revenue sales-баннера и доля субституции базовой воронки не замерены, S8). Качественно: при полной субституции базовых access net impact ≤ 0; знак прогноза документом не защищён.

## 5. Критичные допущения (на которых держится положительный impact)

1. 30% завершивших Tour Install увидят tour update — assumption без замера (S7).
2. 1% конверсия просмотр тура → Access — assumption без замера (S7).
3. Инкрементальность +28/+32 access: ни один из них не субституция базовой конверсии 3.59%/1.78% — implicit assumption, в документе не обсуждается (S7, S8).
4. Неизменность ARPPU $22.03/$25.79 в тестовой воронке — assumption (S7).
5. Суточный горизонт baseline-объёмов и, следовательно, прогноза +$330/+$387 — assumption (S4, S6).

## 6. Риски каннибализации / refunds / guardrails

- **Каннибализация sales-баннера:** документ сам фиксирует, что tour update конкурирует с sales slashes, и заявляет проверку «синергии» (S3), но эффект новой карточки на revenue sales-баннера числом не оценён и guardrail на него не объявлен (S8, S9).
- **Каннибализация базовой воронки:** дополнительные access могут быть перераспределением пользователей, которые купили бы через штатный путь (Access 1d baseline); в модели это не отражено (S8).
- **Нескипаемость тура:** прошлые эксперименты показали, что принудительность влияет на конверсии (S1); фрустрация от нескипаемого тура, запущенного добровольным тапом, отдельным guardrail не покрыта.
- **Refunds / reconversion / LTV:** в документе отсутствуют полностью (S8 — missing).
- **Guardrail-метрики:** не объявлены вовсе (S9 — missing).

## 7. Stop-rule

В документе отсутствует (S13). **Предложение валидатора:** остановка теста при статзначимом падении в тестовой группе (а) конверсии Tour Install End → Access 1d ниже baseline 3.59% (iOS) / 1.78% (Android) или (б) конверсии/выручки sales-баннера на Explore относительно контроля; проверка на середине запланированной длительности.

## 8. Что изменит рекомендацию

**В сторону `launch`:**
- SQL-замер за 2–4 недели: суточные Tour Install End и фактическая видимость зоны карточки на Explorer (подтверждение/замена 30% и достижимости sample 3,920/день iOS) — закрывает К2 (частично) и К4.
- Обоснование 1% конверсии: CTR аналогичных элементов Explore и конверсия существующего tour update → Access из текущего принудительного показа (данные — в заявленных, но не выполненных Research TBD).
- Строка потерь числом: baseline конверсия/выручка sales-баннера у той же аудитории + guardrails (конверсия sales-баннера, базовый Access 1d, uninstall/фрустрационные метрики) — закрывает К3 и S9.
- Зафиксированный post-rollout план (holdout с долей и сроком, либо observational: ARPU новых инсталлов, окно 30/90d, метод сезонного контроля) + stop-rule — закрывает К6.
- Для Android: подтвердить, что 2-дневное окно достаточно для накопления charges по метрике ARPU, либо удлинить.

**В сторону `deprioritize`:**
- Замеры покажут, что net (gain − субституция базовой воронки − потери sales-баннера) ≤ 0; либо владелец бизнес-решения задаст порог минимального impact, который прогноз (+$330/+$387 за период до коррекции) не проходит — сейчас такой порог в документе не задан, и это отмечено явно.
