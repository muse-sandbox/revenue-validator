# HX-01 — pre-launch карточка
(без идентификаторов источника)

## Контекст и цель
Цель проекта — увеличить revenue за счёт адаптации мобильного онбординг-тура (tour) под сегментированную аудиторию. Идея: разделить тур на два сегмента — «learners» (учатся с нуля) и «players» (играют любимые песни). Learners получают полную версию тура со всеми образовательными экранами; players — укороченную версию без вопросов про развитие навыков, советы и т.п.

Опора на прошлые работы: предыдущий эксперимент с целеполаганием в туре определил распределение основных сегментов аудитории («Start learning guitar from scratch» vs «Play my favorite songs»); был командный брейншторм по персонализации ветки тура для начинающих. Текущая версия собирается на базе первого эксперимента про goal-setting и его результатов.

## Предлагаемое изменение (что именно меняем, для кого, где)
Место: онбординг-тур мобильного приложения (iOS и Android).

Итерация 1 (исходный дизайн):
- A (контроль): во все вариации, включая контроль, добавляется экран с сегментирующим вопросом (learners vs players); кроме этого нового экрана контроль не меняется, и выбор ответа на контроль не влияет.
- B (тест): в зависимости от ответа на первом экране — две ветки.
  - Players (ответ «Play my favorite songs» или «Something else»): укороченный тур — удалены все вопросы про развитие, навыки и пение.
  - Learners (ответ «Start learning from scratch»): полный тур, как текущий; удалён экран с вопросом об уровне (предполагаем, что все начинающие); на экране выбора инструмента заголовок заменён на «Which instrument do you want to play?».

Последующие итерации (перезапуски с изменённым набором удаляемых экранов; мотивировки перезапусков опираются на промежуточные данные — `[REDACTED: post-launch вставка]`):
- Итерация 2: learners — без изменений (полный тур); players — укороченный тур, удалены только экраны «How would you prefer to sing your favorite song?» + hook-экран «sounds good» и «How often do you sing?» + hook-экран «our users improve singing skills».
- Итерация 3: learners — укороченный тур с удалением тех же двух «sing»-пар экранов; players — дополнительно удалены экраны «What's your preferred learning style?» и «Do you have a favorite song that you like to sing to your friends?».

## Аудитория / платформа / сценарий
Новые пользователи, проходящие онбординг-тур мобильного приложения; платформы iOS и Android (расчёты раздельно по платформам). Exposure event: Tour Start. Сегментация внутри теста — по ответу на первый сегментирующий экран.

## Baseline
- Конверсия Tour → Access: iOS 0.058, Android 0.021.
- ARPPU: iOS $53, Android $51 (в модели фиксирован, не меняется между вариациями).
- Дневной объём Tour Start (из модели): iOS 14663, Android 14928.

## Reach
- iOS: 14663 Tour Start в день.
- Android: 14928 Tour Start в день.
(Единица «в день» согласуется с планом: sample size / duration = дневному Tour Start; явно в документе не подписана.)

## Денежная модель (цепочка поведение→деньги, все коэффициенты)
Цепочка: Tour Start → Access (конверсия) → Charges → Revenue = Charges × ARPPU.

Модель (значения на день, по табличной модели A/B):
- iOS: Tour Start 14663/14663 (A/B); Tour Install Accesses 847 → 932 (+85); Tour→Access 0.058 → 0.064 (+10%); Charges 325 → 358 (+33); Revenue $17136 → $18850 (+$1714); ARPPU $53 → $53 (без изменений); ARPU $1.169 → $1.286 (+$0.117, +10%).
- Android: Tour Start 14928/14928; Accesses 319 → 351 (+32); Tour→Access 0.021 → 0.024 (+10%); Charges 121 → 133 (+12); Revenue $6168 → $6785 (+$617); ARPPU $51 → $51; ARPU $0.413 → $0.454 (+$0.041, +10%).

Неявный коэффициент Access → Charge (из модели): iOS ≈ 0.384 (325/847), Android ≈ 0.379 (121/319) — константен между вариациями.

## Допущения и их коэффициенты (каждое с типом)
1. Baseline-конверсия Tour→Access 0.058 (iOS) / 0.021 (Android) — observed fact (текущие значения продукта).
2. Дневной объём Tour Start 14663 / 14928 — observed fact.
3. Лифт конверсии +10% от сегментации/укорочения тура — assumption (author opinion, обоснование: показываем каждой аудитории только релевантные вопросы).
4. ARPPU не меняется ($53 iOS / $51 Android) — assumption (forecast-model: монетизация на пользователя с доступом константна).
5. Access→Charge ≈ 0.384 / 0.379 константен между вариациями — forecast-model (неявное допущение таблицы).
6. Revenue растёт пропорционально числу accesses — forecast-model.
